# Browser session infrastructure for a VPS agent

## Decision summary

**Recommended starting point: self-hosted Steel, bound to loopback and reached through an authenticated application route or SSH tunnel.** It is the best fit for the stated preference: a single Docker image, a built-in interactive session view, CDP/Playwright interoperability, and explicit first-party integrations for Gemini Computer Use, browser-use, Stagehand, and MCP. Keep the API and Chrome debugging ports private; Steel explicitly warns not to expose port 9223 publicly.[^steel-docker]

**Lowest-operations alternative: Browserbase.** Choose it if paying for managed infrastructure is preferable to maintaining Chrome, persistence, live viewing, TLS, updates, and resource limits. Its Context + Live View workflow is especially polished for login/MFA handoff.[^bb-contexts][^bb-live]

**Browserless is a strong managed option and the clearest fit if its authenticated-profile workflow or anti-detection stack is preferred.** Its official profile guide directly demonstrates: open a live URL, let a human complete MFA/CAPTCHA, wait for `Browserless.liveComplete`, save the profile, and reuse it.[^bl-profiles]

**Manual Playwright + noVNC is the control/max-privacy fallback, not the simplicity winner.** It avoids a browser-infrastructure vendor, but the application must own Chrome/X display/VNC/websocket lifecycles, authenticated handoff URLs, mutual exclusion between human and agent, persistence, cleanup, and patching.

## Suggested implementation shape

1. **Preferred:** deploy the single-image Steel service with its API/UI/CDP bound to `127.0.0.1` (or an internal Docker network), mount persistent storage, and expose human takeover only through an authenticated application endpoint or an SSH tunnel—not direct public ports.[^steel-docker]
2. Give each account/site a distinct persisted profile; never run simultaneous human and agent input. The orchestrator should transition explicitly: `AUTOMATING -> WAITING_FOR_HUMAN -> HUMAN_CONTROL -> AUTOMATING` only after the user presses a completion control.
3. Treat live-view/debug URLs, websocket URLs, API keys, cookies, and profile archives as credentials: short lifetime where possible, redact from logs, do not commit, and revoke/end the session after handoff.
4. If self-hosted Steel's profile behavior proves insufficient in a spike, move to **Browserbase Contexts + Live View** rather than building more session infrastructure. Browserless is the alternative when its explicit saved-profile/live-completion workflow is a closer match.
